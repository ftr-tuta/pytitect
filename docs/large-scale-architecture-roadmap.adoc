[[decision]]
== Decision and reading contract

Pytitect and Dartitect already provide substantial reliability building blocks.
The next investment should establish correctness under real concurrency and failure,
then close overload and interoperability gaps before expanding the adapter catalog.
Passing unit tests establishes a useful baseline; it does not establish a global service capacity.

This document defines *one target architecture for large, robust applications*.
FastAPI with SQLAlchemy/PostgreSQL is the primary service integration; NATS JetStream is the
reference broker for reproducible integration work. Django is used where its administration,
ORM, and synchronous transactional workflows provide a concrete benefit. Dartitect supplies
the client composition, lifecycle, local persistence boundaries, and synchronization machinery.
This is a reference composition chosen for this roadmap, not automatic SDK configuration or
a claim that one framework wins every workload.

The audience is SDK maintainers, service architects, client engineers, and operators of
consumer applications. This delivery consists of an audit, a design, validation specifications,
and linked issues. Proposed capabilities are not shipped APIs.

The coverage target is complete disposition of the topics in <<ddia-coverage>> and
<<capability-ledger>>: every row has evidence, an owner, and a next action or a justified
boundary. It is not a claim to exhaust all architectural knowledge or guarantee support for
a billion simultaneously active users. Registered users, connected clients, admitted work,
operations per second, data volume, and infrastructure capacity are separate quantities.

The conceptual index uses the first edition of Martin Kleppmann's
https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/[Designing Data-Intensive Applications].
The book's public contents establish topic coverage; its text is not reproduced here.
Recommendations below are this audit's synthesis of repository evidence and primary technical
references, not quotations or assertions that the book mandates this exact stack.

=== Investigations requiring real concurrency

{py-src}/src/pytitect/sqlalchemy/stores.py[SQLAlchemy stores] retain a caller-supplied session,
while {py-src}/src/pytitect/aio/runtime.py[AsyncRelay] invokes settlement operations concurrently.
The direct composition needs a supported short-transaction/session strategy; the presence of
both public types does not establish that sharing one store session across tasks is safe.
SQLAlchemy requires a separate session for concurrent tasks.
https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks[SQLAlchemy concurrency reference].

The checkpoint store's missing-row path reads, then adds a row. Test simultaneous first writers
against real constraints and report the precise loser outcome before classifying it as a bug.
The relay creates one task per claimed message, bounded by the call's limit rather than by its
concurrency setting. Measure task retention, lease waiting time, and concurrent `run_once` calls.
These investigations belong to <<pyt-01>>, <<pyt-03>>, and <<pyt-04>>.

[[ownership]]
== Ownership and inclusion rules

[cols="1,3,3",options="header"]
|===
|Boundary |SDK contribution |Application or infrastructure responsibility
|Pytitect core |Typed outcomes, explicit clocks/limits, ports and finite reference stores
|Business invariants, authorization, schema, transaction placement and external effects
|Pytitect adapters |Explicit integration with caller-supplied framework/provider resources
|Concrete models, migrations, routes, pool configuration, broker topology and process lifecycle
|Dartitect |Native Strict constructor composition, ownership, cancellation, bounded work and sync ports
|Feature policy, local write authority, generated databases, UI, credentials and conflict decisions
|Cross-language contracts |Versioned neutral formats, bounded validation and executable conformance
|Domain schemas, endpoint selection, authorization, routing and semantic mapping
|Platform |No library-owned control plane |Deployment, cells, partition placement, consensus, backups and on-call operation
|===

Preserve dependency-free, side-effect-free `import pytitect`: no settings, environment lookup,
database/network access, logging configuration, registry or optional-adapter import.
Composition is explicit and instance-owned. Never introduce a singleton, ambient service locator,
global runtime, protocol fallback, automatic adapter selection, or library-started worker.

A new Dartitect capability must be neutral, difficult to implement correctly, and remove repeated
infrastructure work. Apply the same test to Pytitect proposals. Consumer rules belong in the
application; reusable non-neutral infrastructure belongs in a project-local extension.
All in-memory references need finite retention and clear process-local, non-durable semantics.

[[cells]]
== One target architecture

=== Components and isolation

Use independent cells with their own serving capacity, transactional write authority, message
processing capacity, and operational limits. A thin application-owned router maps a partition
to its cell. The control plane administers placement and rollout; healthy data-plane operations
must have a defined behavior when that control plane is unavailable.
The isolation model draws on
https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/what-is-a-cell-based-architecture.html[AWS's cell architecture guidance].

[listing]
----
Dartitect client
  local database + durable mutation outbox + session generation
                    |
          consumer-owned public API edge
                    |
           partition-to-cell router
                    |
     +--------------+-------------------------------------+
     | Cell: independently bounded and operated           |
     | FastAPI -> application transaction -> PostgreSQL   |
     |                                  state + outbox    |
     |                                        |           |
     | relay -> NATS JetStream -> inbox + local effects    |
     |                              |                     |
     |                    projections / sync feed         |
     | Optional Django service behind its own boundary    |
     +----------------------------------------------------+
                    |
       explicit asynchronous cross-cell contracts
                    |
         other independently operated cells

Control plane: placement, rollout, authority transfer, recovery
Observability: bounded facts from each independently owned role
----

This is a logical diagram, not deployment code or a new runtime.
The client reaches consumer APIs; server broker credentials and topology remain behind the
service trust boundary. Repeating the same cell design is horizontal expansion of this one
architecture, not a separate small/medium/large product.

Application design requirements:

* Place data that must change atomically within one authority boundary. Identify dependencies
that cross it and give them explicit asynchronous completion and failure states.
* Choose a partition key with a documented skew model. Separate a hot partition's scheduling
budget from aggregate cell capacity; adding cells cannot split a single indivisible invariant.
* Route using an explicit placement generation. A move must prevent the previous writer from
accepting new authoritative work; preserve idempotency identity across routing changes.
* Keep bulk transfer, analytics, replays and administrative jobs within separate resource budgets.
Shared dependencies still need isolation; a shared database or broker can defeat cell isolation.
* Roll out to one cell, evaluate correctness and SLOs, then continue. Define pause and rollback
conditions before the rollout. Pin deployment artifacts and protocol compatibility evidence.

=== FastAPI and selective Django integration

The FastAPI reference root owns its lifespan, dependencies, sessions, publisher, routing and
shutdown. Each request/processing unit borrows the resources it needs and closes only what it
owns. Process replication multiplies memory and connection demand; aggregate those budgets
when sizing a service. See
https://fastapi.tiangolo.com/deployment/concepts/[FastAPI deployment concepts].

Use one SQLAlchemy session per concurrent unit of work and short transactions around state
changes. Claim a finite outbox batch durably, release its transaction, publish externally, and
settle each authoritative claim in its own short transaction. This composition is a target for
<<pyt-04>>, not an assertion that the current session-bound store supplies it automatically.

Django is justified by a service's concrete workflow and ownership needs, including its
administrative tooling and established synchronous ORM transaction path. Keep the whole atomic
unit inside one synchronous function when bridging into async execution; size the bridge and
database pool together. Django 6.1 documents that transactions do not yet work in async mode
and recommends the synchronous bridge.
https://docs.djangoproject.com/en/6.1/topics/async/#queries-the-orm[Django async transaction reference].

Do not make Django mandatory for every microservice or select a framework from a presumed user
count. The two integrations must preserve the same externally observable reliability contract.

[[consistency]]
=== Consistency and authority

Define guarantees per operation. An authoritative write uses one partition's write authority;
a projection or cache read advertises its freshness boundary. Read-your-writes should route to
the authority or wait for a bounded, explicitly identified projection checkpoint. A timeout
must not silently downgrade a promised consistency level.

Local invariants may require atomic updates, uniqueness constraints, locks, version checks or
serializable transactions. PostgreSQL's default Read Committed isolation does not establish
every multi-row invariant. When serialization retries are required, retry the complete local
transaction within the operation's budget, with external effects deferred to the outbox.
https://www.postgresql.org/docs/18/transaction-iso.html[PostgreSQL isolation reference].

Treat partitions and process pauses as normal failure inputs. Expiring ownership is not enough
to protect a resource: the protected write must atomically compare authority under the same
transaction/lock. A stale owner must lose even after a long pause. This requirement is consistent
with https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html[Kleppmann's fencing analysis].

Consensus, leader election and membership belong to the selected infrastructure. No Pytitect or
Dartitect object can create global linearizability, a cross-database atomic commit, or a trusted
global clock. State the availability consequence when a required write authority cannot be
established. Multi-writer conflict resolution and CRDT semantics remain application-selected;
they are not universal defaults for offline synchronization.

[[flows]]
== End-to-end flow contracts

=== Write, publish and consume

[listing]
----
Client        API / producer DB         Relay / broker        Consumer DB
  | request         |                        |                    |
  |---------------> |                        |                    |
  |          begin local transaction         |                    |
  |          validate authority              |                    |
  |          apply state + append outbox     |                    |
  |          commit                          |                    |
  |<-- local result / durable acceptance     |                    |
  |                 |<-- claim + commit -----|                    |
  |                 |                  publish + confirmation     |
  |                 |<-- settle claim -------|                    |
  |                 |                        |---- delivery ----->|
  |                 |                        |        reserve inbox
  |                 |                        |        state + outbox
  |                 |                        |        complete inbox
  |                 |                        |        commit
  |                 |                        |<------- ACK --------|
----

The API response describes the local commit or acceptance only. A downstream workflow's final
result requires its own durable receipt/status. A lost response is an uncertain outcome:
reconcile using the original idempotency identity before issuing a new logical operation.

Idempotency identity includes a consumer-defined namespace and operation scope. Reject a
reused identity with a conflicting request fingerprint according to the existing coordinator
contract. Retain accepted/uncertain records across the complete retry and reconciliation window.
Broker deduplication is an optimization; it does not replace the receiving inbox.

An external system that neither accepts an idempotency identity nor offers reconciliation
cannot be made exactly once by a local outbox. Record uncertainty and require the application's
compensation or reconciliation decision. Do not retry that uncertainty blindly.

=== Query and derived-state visibility

Queries select authoritative or explicitly stale-tolerant reads at composition. Bound query
time, returned rows, object hydration, response bytes and any fan-out. A request timeout includes
queue and pool wait. Paginate using a stable ordering and a documented snapshot/continuation
contract; an offset or cursor alone does not prove consistency under concurrent writes.

Caches and materialized views are derived state. Choose freshness, invalidation, stampede
control, negative-cache retention and deletion propagation in the application. A cache outage
must not unleash an unlimited fallback load on the database. Cache keys and authorization
scope must agree; cache behavior must not substitute for an authorization decision.

=== Client mutation, delta and restart

[listing]
----
Local transaction: application state + durable mutation identity + outbox
  -> bounded delivery attempt using the same identity
  -> server local transaction + receipt
  -> client reconciliation of confirmed / rejected / uncertain result

Confirmed local checkpoint
  -> bounded delta request
  -> validate version, limits and active session generation
  -> local transaction: apply page and compare required fencing authority
  -> persist checkpoint only after the corresponding local state is durable
  -> request the next page

Restart
  -> recover durable operations and confirmed coverage
  -> reconcile uncertain outcomes
  -> resume bounded work; never trust an in-memory receipt as durability
----

If the data and checkpoint use separate commits, a crash may replay a page; the page application
must tolerate it. A checkpoint must never advance beyond durable coverage. If the contract
requires atomic data-plus-checkpoint commit, supply one consumer transaction supporting both;
the SDK cannot synthesize that guarantee across stores.

An expired cursor or a removed retention window triggers an explicit bounded bootstrap path.
Preserve unresolved local mutations through resynchronization. Late responses from an obsolete
session generation cannot publish into the replacement session. Conflict classification,
merging, user-visible reconciliation and deletion semantics remain application-owned.

[[persistence]]
== Persistence, retention and recovery

Production store conformance needs real transactions and simultaneous independent connections.
Test empty and populated state, first-writer races, duplicate inserts, compare-and-set losers,
expired claims, rollbacks, deadlocks, cancellation, and process interruption. Verify the state
from a fresh connection after each event, not only from a cached ORM object.

Application storage requirements:

* Design indexes against actual claim, deduplication, checkpoint and retention queries.
Measure query plans, locks, rows scanned, table/index growth and maintenance interference.
`SKIP LOCKED` supports competing claimers; it does not create application event ordering.
* Bound each transaction's statements, rows, payload and duration. Configure statement, lock
and pool timeouts explicitly. Keep network publication outside database transactions.
* Allocate connection budgets across API replicas, relays, consumers, maintenance and admin
access. Autoscaling a process count without a connection budget can overload PostgreSQL.
* Define separate retention windows for inbox completion, idempotency results, uncertain
receipts, replay, quarantine, tombstones and event history. A single TTL is insufficient.
* Cover outages, client offline intervals, delayed broker redelivery, deployment rollback and
operator replay when deriving retention. If retained history is insufficient, reject the old
continuation explicitly and use a supported recovery path.
* Run maintenance in bounded batches with an explicit cutoff, dry-run evidence, checkpoints,
and a rate budget. Preserve any authority token whose reuse could admit a stale writer.

Backups must include the state required to reconcile previously acknowledged work. PostgreSQL
PITR depends on a usable base backup and the required WAL sequence; restoring must be practiced,
including outbox/inbox/checkpoint relationships.
https://www.postgresql.org/docs/18/continuous-archiving.html[PostgreSQL PITR reference].
Encrypt and restrict backups through consumer infrastructure and verify key availability during
restore. Define what survives a regional loss and which accepted operations may require
reconciliation after restoration. A replica alone is not a tested backup strategy.

[[regions]]
== Regional operation and partition movement

The reference design has one active write authority per partition, with explicitly managed
replication and takeover. Independent partitions may be active in different regions. This does
not imply unrestricted writes to the same partition in every region.

Synchronous and asynchronous replication trade acknowledgment latency, availability and potential
data loss differently. Record the configured durability boundary and replication lag, and test
promotion under that actual configuration.
https://www.postgresql.org/docs/18/warm-standby.html[PostgreSQL replication reference].

The application/platform must produce a failover runbook that:

. Identifies the last accepted authority generation and prevents the former writer from
committing after the replacement becomes authoritative.
. Determines durable coverage, replica lag and the permitted recovery point before promotion.
. Reconciles outbox publication, inbox completion, receipts and checkpoints at the new authority.
. Updates routing without changing logical operation IDs; bounds redirected and retried traffic.
. Confirms freshness guarantees and restores traffic progressively under a capacity budget.
. Records recovery time and any lost, duplicated or unresolved work before allowing failback.

Move partitions using a versioned placement procedure with verification and an explicit cutover.
Retain the source until the target's state and continuation coverage are verified. Schema evolution
and data movement are consumer operations; this repository ships no partition router or migration.
Distributed transactions across cells and global event ordering are excluded defaults because
they couple failure and latency across otherwise independent authorities.

[[messaging]]
== Messaging and overload

=== Broker semantics and bounded delivery

NATS JetStream is the reference integration, with explicit durable consumption, pull demand,
acknowledgment deadlines, retention and redelivery configuration owned by the application.
Bound prefetch against handler capacity and time spent waiting before processing; the broker's
acknowledgment timer and the local reservation timer are different authorities.
https://docs.nats.io/learn/jetstream/pull-consumers[NATS consumer reference].

AWS EventBridge/SQS remains an explicit alternative adapter with its own capability evidence.
SQS Standard can redeliver messages and requires idempotent processing.
https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html[SQS delivery reference].
Do not infer ordering parity from sharing an envelope. The audited Pytitect release rejects
ordered profiles and does not implement Kafka or RabbitMQ. Additional transports require a
demonstrated workload need and the same real failure suite before they enter the roadmap.

For application ordering, define the key, sequence authority, gap policy, replay boundary and
maximum buffered disorder. Concurrent publishing and retries can reorder completion even when
rows were claimed in order. No timestamp, UUID or global in-memory counter supplies a distributed
total order. Event identity, correlation, causation and partition identity serve different roles.

=== Coordinated overload policy

The target contract bounds admitted work, queued work, in-flight bytes, active keys, pool wait,
retry work and recovery work. Saturation returns a typed outcome that the consumer can map to
its public protocol. Rate limits are local unless backed by an explicit distributed authority;
never describe a per-process bucket as a fleet-wide quota.

Clients and servers need a shared strategy for overload because repeated rejected traffic still
consumes resources. This principle is supported by
https://sre.google/sre-book/handling-overload/[Google SRE's overload guidance].
The SDK work proposed here is explicit policy and ports; request classification and fair-share
allocation remain consumer decisions.

Specify one end-to-end deadline and a retry owner for each operation. Count time spent in
admission, pools, calls, retry delays and cleanup. Use a monotonic elapsed clock locally and
separate it from UTC timestamps used in persisted records. Cross-host deadline metadata needs
an explicit trust boundary, maximum budget and clock-skew treatment.

Use saturating backoff arithmetic, injected randomness and a finite attempt/elapsed budget.
The reference composition opts into full jitter; preserve existing public constructor behavior
unless a reviewed compatibility change says otherwise. A retry cannot outlive the operation's
deadline or turn a typed uncertain outcome into another execution.

Coordinate HTTP feedback with the client's retry policy. `Retry-After` can encode a date or a
delay; parsing it does not authorize a retry of a non-idempotent operation.
https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3[HTTP Retry-After semantics].
An excessive delay should yield a deferred/stopped result rather than retrying earlier than a
valid server minimum. Invalid hints require an explicit policy, never hidden fallback.

Use bulkheads for independent dependencies and work classes, single-flight for eligible
duplicate reads, and breakers whose scope and recovery probes are bounded. Do not coalesce
distinct mutations or authorization scopes. Reconnect, token refresh, background sync and
periodic maintenance must not synchronize into an unbounded fleet-wide retry wave.

[[interop]]
== Python--Dart contracts and client evolution

Pytitect already publishes `titect-sync/1` and `titect-message/1` bundles; independent versioning
and hashes are useful foundations. Dartitect already has mutation, sync, resilience and lifecycle
primitives. The missing evidence is their compatibility across a real public boundary.
See {py-src}/docs/event-platform-interoperability.md[message interoperability] and
{dart-src}/packages/dartitect_sync/README.md[Dartitect sync].

The executable conformance target is:

* Verify both repositories against an immutable bundle identity and every declared fixture hash.
Decode positive fixtures, reject negative fixtures, and compare canonical bytes where required.
* Exercise numeric boundaries, Unicode and escaping, duplicate/unknown members, UTC precision,
nesting, collection counts, metadata and encoded byte limits. Test Dart VM and web where declared.
* Apply allocation limits at the parsing boundary; post-allocation validation alone is not a
memory bound. Document which checks the transport, decoder and model validator each enforce.
* Preserve existing `/1` semantics. New mandatory fields or incompatible acceptance rules
require an explicit compatibility/version decision and a rolling-upgrade test matrix.
* Keep server cursors opaque on the client; transport does not imply possession of server
signing/encryption keys. Translate neutral outcomes without inventing domain conflict policy.

Canonicalization must follow the declared profile rather than assuming that sorted JSON in
two runtimes produces identical bytes for all numbers and strings.
https://www.rfc-editor.org/rfc/rfc8785.html[RFC 8785 reference].
The audit does not assert that every existing message encoder is RFC 8785; prove the exact
bundle's numeric and serialization contract before adopting that label.

Rollout tests must cover old-client/new-server and new-client/old-server combinations permitted
by the support policy, deliberate rejection of incompatible versions, expired cursors,
partially committed batches and interrupted bootstrap. Keep fixtures neutral and public.

On clients, bound stored pending mutations, bootstrap pages, retained family entries, progress
history, simultaneous dataset work and telemetry queues. Reuse existing Dartitect incremental
and resilience primitives instead of creating a competing runtime. Handle disk exhaustion and
platform background limits as explicit failures. A process-local sync lease does not coordinate
multiple tabs, processes or devices without a storage authority that actually spans them.

[[derived]]
== Derived data, batch processing and workflow recovery

Transactional state is the reference write authority. Projections, caches, search and analytics
derive from it using explicit, recoverable propagation. Separate operational queries from large
analytical scans and exports. Application-selected CDC may reduce polling costs, but it needs
its own capture-position, retention and restart evidence; it does not remove inbox semantics.

Projection rebuilds need a fixed target coverage, bounded pages, versioned reducers, durable
progress and a verified cutover to the replacement view. Do not mix checkpoints across partitions
or imply a global position beyond the selected event store. Reprocessing needs deterministic
inputs and explicit handling of changed code, deleted records and authorization-relevant data.

For stream-derived state, define event time versus processing time, late arrivals, duplicates,
gap detection, watermarks, bounded joins and correction policy only where the application uses
them. Pytitect's current event/projection contracts are not a general stream-processing engine.
Batch engines, analytical warehouses and indexing backends remain external systems.

Event sourcing is optional for a domain that requires an authoritative event history. It is not
a mandatory rewrite of CRUD services. Process managers and compensations are explicit decisions;
compensation is not automatic rollback of an external effect. Durable timers/jobs require the
same claim, fencing, retry and retention evidence as message processing. Extend conformance
before treating additional model slots as implemented durable stores: <<pyt-08>>.

[[operations]]
== Operations, observability and safe rollout

Record correctness alongside performance: accepted operations recovered, duplicate local effects,
stale writes rejected, checkpoint coverage, unresolved receipts, oldest pending work and rebuild
progress. Separate API, relay, consumer, timer and projection readiness; a broker outage should
affect an API only according to its selected durability/backlog policy.

Define SLIs and SLOs around user-visible success, latency, durability and freshness. Keep the
measurement boundary and denominator explicit, including rejected and timed-out work. Tail latency
and freshness distributions are more informative than averages alone.
https://sre.google/sre-book/service-level-objectives/[Google SRE SLO reference].

The proposed runtime instrumentation emits fixed event names and allowlisted attributes through
injected sinks. Bound both attribute count and possible label values. A map with 32 arbitrary
values is not a cardinality guarantee. Test that sink failures cannot change commit, ACK or
cancellation behavior. Exporters, sampling, alert destinations and dashboards remain consumer-owned.

Trace Context is transport metadata, not authorization or message identity. Validate it at the
boundary and propagate only the declared context; keep broker envelopes stable.
https://www.w3.org/TR/trace-context/[W3C Trace Context reference].
Logs and traces must not contain raw bodies, credentials, cookies, tokens, idempotency keys,
DSNs, private paths or identifiers smuggled into unrestricted labels.

Operational acceptance requires runbooks for backlog growth, poison deliveries, exhausted retry
budgets, missing history, authority transfer, restore and a failed rollout. Stop admission before
draining; bound the grace period; cancel cooperatively; release resources in dependency order.
Cancellation is not proof that a remote operation failed or that a database commit rolled back.
After ambiguous completion, inspect durable state before replaying work.

[[security]]
== Trust, privacy and tenant isolation

Security policy is consumer-owned, but boundaries must make correct integration possible.
Authenticate and authorize every public operation and continuation in its current session;
an opaque identifier or validated protocol proof is not authorization. Keep scope binding
consistent across idempotency, caches, inboxes, cursors and storage access.

Apply request, decoded-body and decompression limits before expensive work. Separate untrusted
client claims from trusted server policy for deadlines, quotas and routing. Require explicit
key resolution and rotation procedures, bounded replay windows, audience/context validation and
revocation behavior. Exercise obsolete-session responses and replay after key rotation in the
paired tests without embedding secrets in fixtures.

Deletion and retention must reach caches, projections, offline replicas, exports and backups
according to the application's policy. Protect quarantine access and use digest/minimal metadata
by default. Payload retention needs an explicit finite policy. Security vulnerabilities belong
in the repositories' private reporting process; public issues contain neutral reliability and
enhancement evidence only.

[[capacity]]
== Capacity model and performance evidence

There is no measured fleet-capacity result in this audit. Use one declared workload for the
reference architecture, then vary its parameters for sensitivity and failure testing. Those
variations are experiments on the same design, not separate architecture tiers.

[cols="1,3,2",options="header"]
|===
|Input |Required definition |Measurement boundary
|Population and activity |Registered, connected, active and concurrently executing clients |Client and edge
|Operation mix |Read/write/sync/replay frequencies, fan-out and payload distributions |Public operation through terminal result
|Skew |Partition popularity, hot-key concentration and tenant imbalance |Partition and cell
|Resources |CPU, RAM, storage IOPS, network, pool size, broker retention and topology |Process, cell and shared dependencies
|Service objectives |Latency percentiles, availability, durability, freshness, RPO and RTO |Named operation and observation window
|Failure allowance |Dependency slowdown, cell loss, reconnect surge and recovery headroom |Same workload during and after faults
|===

Use dimensionally explicit calculations:

[listing]
----
offered operations/s = active clients * operations/client/s
dependency calls/s = offered operations/s * calls/operation * attempt amplification
mean in-flight work = measured throughput/s * mean residence time in seconds
payload bandwidth bytes/s = delivered messages/s * mean encoded bytes/message
backlog drain seconds ~= queued messages / (service rate - admitted arrival rate)
retained bytes ~= arrival rate * retention seconds * mean stored bytes
----

These are planning relationships, not benchmark results. The in-flight relationship assumes a
stable measurement boundary; the drain estimate requires service rate greater than arrival rate.
Storage estimates additionally need index, WAL, replica and metadata overhead. A partition's
capacity can dominate long before aggregate CPU is exhausted. Avoid linear extrapolation from
one process to a worldwide fleet without measuring shared bottlenecks and failure headroom.

The benchmark specification in <<pyt-09>> must record commit, wheel/bundle hashes, dependency
versions, topology, machine limits, dataset generator/seed, warmup, duration and offered load.
Use open arrival scheduling or account for coordinated omission so a slower server does not
silently reduce the load being measured. Report failed/timed-out work, not just successful
latency. Establish the load generator's own headroom before trusting saturation results.

Measure p50/p95/p99 latency, throughput, CPU, RSS, event-loop lag, retained tasks, pool wait,
database locks, oldest backlog age, duplicate suppression, retry amplification and recovery time.
For Dartitect include retained bytes, first useful page, cancellation-to-quiescence and session
replacement behavior. Run sustained load and overload/recovery, not only microbenchmarks.
Track cost per useful committed operation including replication, egress and operational storage.

    ))
    await AsyncRelay(
        store, Publisher(),
        RoutingTable([Route("example.probe.v1", "probe")]), clock=clock,
    ).run_once(limit=1)
    print("retry offset seconds:", (store.retry_at - clock.now()).total_seconds())

    clock = Clock()

    async def handler(msg, context):
        clock.value += timedelta(seconds=2)
        return Decision(result=None)

    consumer = AsyncConsumer(
        consumer="probe", namespace="probe", handler=handler,
        unit_of_work=InMemoryAsyncUnitOfWorkFactory(),
        quarantine=InMemoryRejectedDeliveryStore(), clock=clock,
        reservation_ttl=timedelta(seconds=1),
    )
    print("expired reservation:", await consumer.process(Delivery()))

asyncio.run(main())
try:
    print(RetryPolicy(max_attempts=100).delay(60))
except OverflowError:
    print("retry arithmetic: OverflowError")

A real PostgreSQL test demonstrated that an `UPDATE` expiry predicate may be evaluated before a

must return stale. This is database evidence in addition to injected-clock unit tests.
